# Приёмка требований перед выпуском и закрытием Issues

Зелёная сборка подтверждает только выполненные тесты. Она не доказывает реализацию всех требований. Issues закрываются после проверки всей актуальной постановки на точном выпускаемом артефакте. Публикация приложения разрешается только отдельной командой владельца.

## Актуальная постановка

`requirements.json` — реестр 106 задач: исторически закрытых исправлений и открытых согласованных дополнений для повторной проверки после аудита 0.46. Метка `pending` означает отсутствие новой приёмки, а не доказанную неисправность. Это не готовый отчёт успешных испытаний.

Перед каждым выпуском:

1. Выгрузить все Issues (включая закрытые и все страницы), прочитать постановки и поздние комментарии. Дополнить реестр новыми согласованными задачами. Для каждой задачи разложить актуальные условия на отдельные проверяемые требования; заголовок Issue не заменяет список условий.
2. При противоречии действует последнее согласованное владельцем уточнение. Вписать исходное условие, новое правило и ссылку на решение. Частично заменённую задачу не считать целиком отменённой. Реализованный старый пункт не возвращать вопреки новому решению.
3. Если трактовку нельзя определить из согласований, предложить вариант и уточнить у владельца. Не превращать предложенные, но не согласованные числа/макеты в обязательную спецификацию.
4. Указать по каждому действующему условию код, сценарий, ожидаемый и фактический результат и доказательство. Отдельно отметить «реализовано в коде», «проверено автоматически», «проверено на Windows вручную», «не проверено». Наличие обработчика или скриншота макета — не приёмка.
5. Для порционных выпусков сверить всю выбранную порцию из `release-batches.json` и обязательные регрессии, а не только файлы diff; остальные задачи остаются в назначенных выпусках. Критический дефект безопасности клиента блокирует любой выпуск независимо от порции: общие стили/статусы/координация меняют старые функции. Непроверенное/недоделанное условие не закрывать; указать открытую задачу, причину и границы. Изменение исходников после проверки требует новой точной сборки и актуальных доказательств.

## Обязательный контроль клиента

Проверять в изолированном Windows-стенде без воздействия на производственные компьютеры:

- Повторные клики, две консоли, разные имена одного endpoint: единственный собственный сборщик/исполнитель, нет очереди дубликатов и накопления Probe/WinRM. Зафиксировать число процессов/задач до, во время и после, а не только цвет значка.
- Удаление, запрет переустановки, явное включение и восстановление зависшего сборщика. Успех только после проверки постусловий и свежего снимка; Partial/отказ доступа/занятость не выдавать за успех.
- Перезагрузка/потеря питания/остановка своей задачи на поиске, скачивании, установке и перед записью результата; восстановление с новой загрузкой и неизвестным исходом. Не продолжать с сохранённого процента; проверять фактическое состояние, не создавать второй установщик.
- Долгий живой опрос, зависший опрос, отмена и принудительное завершение только точно принадлежащего сборщика после неудачи штатной отмены. PID проверять вместе со временем запуска/назначением. Системные службы и процессы установки автоматически не завершать.
- VPN потерян/возвращён, старый ответ после нового, неполный/повреждённый снимок, обновление сборщика после ошибок. Master OFF до старта/во время ожидания/после перезапуска; не запускать новые чтения из отменённого поколения.
- Ошибка сброса кэша, частичное восстановление служб, потеря первичной ошибки: диагностика сохраняется, ложного успеха/дальнейшей установки нет.

## Статусы и интерфейс

Один набор исходных фактов проверить в шапке, дереве, последних клиентах, трёх критериях, отчёте, истории и списке внимания. Проверить старый WSUS Failed + новая успешная установка + reboot, положительные флаги в той же загрузке, новый boot + неполные флаги, отрицательные свежие флаги, старый отчёт после нового чтения. Возраст сам по себе не отменяет последнюю полную готовность.

Фактически отрисовать все режимы, три темы, широкое и узкое окно, масштабирование и длинные тексты. Проверить рамки/фоны/значки не только трёх критериев, но и вложенных служебных блоков. Поиск, копирование и фильтры находятся в заголовках; действия — у соответствующей причины. Фоновое завершение чужого запуска не меняет выбранного компьютера/вкладку, прокрутку и выделение. Проверить 400+ строк, большую историю и отсутствие блокирующей работы на UI-потоке.

## Машинный отчёт и блокировка публикации

После успешного Windows run создать `docs/acceptance/<версия>.json` на основе `template.json`. Нельзя копировать демонстрационные результаты как прошедшие. Заполнить:

- `version`, `commit`, `run_id`, `sha256` — точно как для выпускаемого ZIP;
- `registry_sha256` — SHA-256 байтов текущего `requirements.json`;
- `reviewer`, `reviewed_at` — кто и когда выполнил сверку;
- `batch_plan_sha256` — SHA-256 байтов согласованного `release-batches.json`;
- `issues` — ровно все Issues выбранной версии из плана порций; каждая должна иметь статус `passed` и проверки **каждого** действующего условия. Полная раскладка всех задач/условий по порциям также проверяется; пропуски и дубли запрещены;
- `passed`: все проверки прошли на указанном коммите, указаны сценарии, ожидание/факт, ссылки на логи/снимки/артефакты;
- В выбранной порции `deferred` запрещён. Остальные задачи остаются в своих последующих порциях; они не считаются принятыми.
- В выбранной порции `superseded` запрещён. Согласованную замену сначала отражают в реестре условий и плане; затем проверяют действующие условия.
- `scenarios` — все обязательные регрессии из реестра, без пропусков и отложенных результатов;
- `close_issues` — только полностью прошедшие задачи. Смысловые замены оформлять отдельно со ссылкой, не закрывать как выполненное.

`acceptance_gate.py` проверяет покрытие реестра, результаты и идентичность сборки **до сетевых действий публикации**. `publish: false` позволяет подготовить артефакт, но не разрешает закрытие задач. Для старых релизов без отчёта повторная публикация также блокируется; ничего не заполнять фиктивно ради обхода. Существующие опубликованные релизы остаются нетронутыми.

Ограничение: валидатор проверяет структуру и полноту заявленного отчёта, но не может доказать честность произвольной ссылки или качество ручной проверки. Не заменять реальные наблюдения формальным JSON. Автоматического закрытия Issues нет: перед закрытием сверить `close_issues`, фактические результаты и комментарий приёмки. Слияние PR само по себе не закрывает функциональные задачи; не применять `Fixes/Closes` до приёмки.

## Комментарий закрытия

Для каждой закрываемой задачи: актуальные требования и чем заменены старые; исходный commit; run и хеш артефакта; отдельные проверки с результатами/ссылками; оставшиеся ограничения. При любом непроверенном действующем условии — оставить открытой или переоткрыть, не обещать безусловную гарантию отсутствия ошибок.


### Покрытие отдельных условий

Перед `passed` в каждой задаче реестра должен быть вручную сверенный список `conditions`: объекты с уникальным `id` и актуальным `requirement`. В каждом элементе `checks` отчёта обязателен `condition_id`. Валидатор требует покрыть все зарегистрированные условия; одной общей проверкой нельзя закрыть несколько непроверенных условий. Новые задачи сначала включаются в реестр. Индекс исходных абзацев `0.47-condition-inventory.json` не является таким списком: в нём есть исторический контекст, который ещё нужно классифицировать. Отсутствие `conditions` блокирует заявление `passed`, а не заполняется автоматически из заголовка. Никакая автоматическая сверка идентификаторов не заменяет проверку содержания доказательств.
