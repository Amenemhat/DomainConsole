# Публикация версии

Новый релиз публикуется только после команды владельца на выпуск версии. Коммиты исходников сами по себе не создают релизы.

## Порядок

1. Завершить согласованные изменения, обновить версию в csproj и описание фактического функционала в README.
2. Дождаться успешного `Build Windows application` для точного коммита на main. Скачать пакет `DomainConsole-Windows-x64`, проверить ZIP и SHA-256, просмотреть снимки интерфейса.
3. Подготовить `docs/releases/<версия>.md`: изменения, исправленные Issues, проверка, ограничения и инструкция обновления с сохранением Data.
4. Отдельным завершающим коммитом заполнить `.github/release-request.json`: версия, номер успешного run, точный коммит, SHA-256 проверенного ZIP, `publish: true`.
5. Workflow `Publish verified release` повторно проверяет исходный успешный run, совпадение версии и коммита, SHA-256, целостность ZIP и отсутствие Data. Публикуется тот же артефакт, без повторной компиляции.
6. Сначала создаётся черновик и загружаются ZIP с `SHA256SUMS.txt`; только после загрузки файлов релиз становится публичным. Существующие теги и отличающиеся файлы не перезаписываются.
7. Проверить ссылку Releases, обновить ссылку текущей версии в README и записать результат в соответствующие Issues. Закрывать задачи по фактической готовности и проверке, не только по наличию коммита.

## Текущая настройка

Запрос для 0.24 содержит `publish: false`: это проверка механизма на уже проверенном артефакте. Она **не создаёт тег или релиз**, не меняет приложение и не выпускает новую версию. Следующий согласованный выпуск публикуется через тот же workflow с новым проверенным запросом.

Устаревший или истёкший артефакт, неуспешная сборка, несовпадение исходников/версии/контрольной суммы останавливают публикацию. Если архив был пересобран, сначала проверяется новый артефакт, затем явно обновляются run и checksum в запросе.
