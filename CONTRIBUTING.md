# Работа с замечаниями и выпусками

## Issues

Любую новую правку сначала фиксируем в GitHub Issues. Одна самостоятельная проблема или функция — один Issue. Перед созданием проверяем существующие записи; дополнения добавляем к соответствующей задаче. Указываем наблюдаемое поведение, желаемое поведение, версию и проверяемые критерии приёмки.

Предложения помечаются как план, а не как уже реализованные функции. В README перечисляется только функционал выпущенной версии; будущие возможности вынесены отдельно со ссылками на Issues.

Для ошибок используйте шаблон «Ошибка», для новых возможностей — «Предложение». Версия Windows консоли и клиента, оболочка CMD/PowerShell, время события и режим операции помогают воспроизвести проблему.

## Накопление изменений

Замечание в обсуждении или новый Issue не являются командой немедленно менять приложение и выпускать версию. Владелец проекта предпочитает накапливать мелкие правки и отдельно давать команду на обновление.

Во время реализации связываем изменения с номерами Issues. Для проверки записываем, что изменилось, какие Windows-проверки прошли и что ещё требуется проверить в домене. Не закрываем задачу только из-за наличия коммита; отражаем её фактический этап и результат проверки. После применения и успешных проверок добавляем ссылки на коммиты, проверенную сборку и релиз, затем закрываем Issue как completed. Если часть работы остаётся, задача остаётся открытой.

## Выпуск

Версия выпускается после отдельной команды владельца, завершения реализации и успешных проверок. В Releases публикуем готовый Windows ZIP, SHA-256, список изменений и инструкцию обновления с сохранением Data. Исходники и пакет должны относиться к одному проверенному коммиту. Промежуточные сборки автоматически релизами не становятся.

Технический порядок: [docs/RELEASING.md](docs/RELEASING.md).
